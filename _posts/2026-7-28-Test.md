# Working with the Achukkowa API Gateway

Integrating with third-party APIs is not always straightforward—especially when those APIs rely on outdated authentication methods, expose credentials directly, or lack the security controls expected in a modern enterprise environment.

The **Achukkowa API Gateway** provides a secure intermediary between internal applications and external services. Hosted in **Oracle Cloud Infrastructure (OCI)**, it uses **OCI Container Instances** to run C# proxy services and **OCI API Gateway** to route, secure, and manage incoming requests.

This article explains the gateway's architecture, how requests flow through the platform, and what developers should consider when building or maintaining an integration.

## Why Achukkowa Exists

Many third-party APIs were not designed with modern security requirements in mind. Common problems include:

- Static API keys embedded in applications
- Credentials passed through query strings
- Limited or nonexistent authentication
- Inconsistent authorization controls
- No centralized request logging
- Weak transport or certificate configuration
- Credentials shared across multiple consumers

Connecting internal applications directly to these services increases risk. It also spreads third-party integration logic across multiple applications, making credential rotation, monitoring, and maintenance more difficult.

Achukkowa addresses this by placing a controlled proxy between internal consumers and external providers.

Instead of calling a third-party API directly, an application calls Achukkowa. The gateway validates and routes the request, while the C# proxy handles the external provider's authentication and communication requirements.

## Architecture Overview

Achukkowa is built primarily from two OCI services:

1. **OCI API Gateway**, which provides the public or internal-facing API endpoint and handles request routing.
2. **OCI Container Instances**, which host the C# proxy applications that communicate with third-party APIs.

A typical request follows this path:

```text
Internal Application
        |
        v
OCI API Gateway
        |
        v
C# Proxy on OCI Container Instances
        |
        v
Third-Party API
```

Each component has a distinct responsibility.

### OCI API Gateway

OCI API Gateway acts as the entry point for consumers. It can be used to:

- Define routes and HTTP methods
- Restrict access to approved clients
- Enforce authentication requirements
- Apply request policies
- Control cross-origin resource sharing
- Standardize externally visible endpoints
- Forward traffic to the appropriate containerized proxy

Keeping routing and access policies at the gateway layer allows the C# application to remain focused on integration logic.

### OCI Container Instances

The proxy services run as containers using OCI Container Instances.

Container Instances provide an isolated container runtime without requiring the team to manage a full Kubernetes cluster or a fleet of virtual machines.

The C# proxy is responsible for tasks such as:

- Constructing requests for the third-party API
- Adding third-party credentials
- Transforming request and response payloads
- Normalizing HTTP status codes
- Enforcing integration-specific validation
- Applying timeouts and retry rules
- Filtering sensitive response data
- Recording operational logs

The proxy acts as an adapter between the internal API contract and the third party's API contract.

## How a Request Is Processed

Consider an internal application that needs customer information from a third-party provider.

The internal application sends a request to an Achukkowa endpoint:

```http
GET /customers/12345
Authorization: Bearer <internal-access-token>
```

OCI API Gateway evaluates the request and determines whether the caller is permitted to use the route. It then forwards the request to the appropriate C# container.

The proxy may convert that request into the format required by the third-party API:

```http
GET /legacy/customer?id=12345
X-Api-Key: <provider-api-key>
```

The third-party credential is added inside the controlled proxy environment. It is never exposed to the original caller.

When the third party responds, the proxy can map the provider-specific response into a consistent internal format before returning it through OCI API Gateway.

For example, a third-party response might look like this:

```json
{
  "cust_id": "12345",
  "cust_nm": "Ada Lovelace",
  "status_cd": "A"
}
```

Achukkowa could return a cleaner contract:

```json
{
  "customerId": "12345",
  "name": "Ada Lovelace",
  "status": "active"
}
```

This separation prevents internal applications from becoming tightly coupled to a third party's naming conventions or implementation details.

## Building a C# Proxy

A proxy service can be implemented using ASP.NET Core and `HttpClient`.

The following simplified example forwards a request to a third-party customer endpoint:

```csharp
using System.Net.Http.Headers;
using Microsoft.AspNetCore.Mvc;

namespace Achukkowa.Proxy.Controllers;

[ApiController]
[Route("customers")]
public sealed class CustomersController : ControllerBase
{
    private readonly HttpClient _httpClient;
    private readonly IConfiguration _configuration;
    private readonly ILogger<CustomersController> _logger;

    public CustomersController(
        HttpClient httpClient,
        IConfiguration configuration,
        ILogger<CustomersController> logger)
    {
        _httpClient = httpClient;
        _configuration = configuration;
        _logger = logger;
    }

    [HttpGet("{customerId}")]
    public async Task<IActionResult> GetCustomer(
        string customerId,
        CancellationToken cancellationToken)
    {
        if (string.IsNullOrWhiteSpace(customerId))
        {
            return BadRequest(new
            {
                error = "A customer ID is required."
            });
        }

        var baseUrl = _configuration["ThirdPartyApi:BaseUrl"];
        var apiKey = _configuration["ThirdPartyApi:ApiKey"];

        if (string.IsNullOrWhiteSpace(baseUrl) ||
            string.IsNullOrWhiteSpace(apiKey))
        {
            _logger.LogError(
                "The third-party API configuration is incomplete.");

            return StatusCode(
                StatusCodes.Status500InternalServerError,
                new
                {
                    error = "The integration is not configured correctly."
                });
        }

        var requestUri =
            $"{baseUrl.TrimEnd('/')}/legacy/customer" +
            $"?id={Uri.EscapeDataString(customerId)}";

        using var request = new HttpRequestMessage(
            HttpMethod.Get,
            requestUri);

        request.Headers.Add("X-Api-Key", apiKey);
        request.Headers.Accept.Add(
            new MediaTypeWithQualityHeaderValue("application/json"));

        try
        {
            using var response = await _httpClient.SendAsync(
                request,
                HttpCompletionOption.ResponseHeadersRead,
                cancellationToken);

            var responseBody = await response.Content.ReadAsStringAsync(
                cancellationToken);

            if (!response.IsSuccessStatusCode)
            {
                _logger.LogWarning(
                    "The third-party customer request failed with status {StatusCode}.",
                    (int)response.StatusCode);

                return StatusCode(
                    StatusCodes.Status502BadGateway,
                    new
                    {
                        error = "The upstream service could not complete the request."
                    });
            }

            return Content(
                responseBody,
                "application/json");
        }
        catch (TaskCanceledException)
            when (!cancellationToken.IsCancellationRequested)
        {
            _logger.LogWarning(
                "The third-party customer request timed out.");

            return StatusCode(
                StatusCodes.Status504GatewayTimeout,
                new
                {
                    error = "The upstream service timed out."
                });
        }
        catch (HttpRequestException exception)
        {
            _logger.LogError(
                exception,
                "An error occurred while contacting the third-party API.");

            return StatusCode(
                StatusCodes.Status502BadGateway,
                new
                {
                    error = "The upstream service is unavailable."
                });
        }
    }
}
```

This example is intentionally simple. A production proxy should also consider typed clients, structured response models, resilience policies, request correlation, and centralized exception handling.

## Configuring `HttpClient`

C# proxy services should use `IHttpClientFactory` rather than creating a new `HttpClient` for each request.

A client can be registered in `Program.cs`:

```csharp
var builder = WebApplication.CreateBuilder(args);

builder.Services.AddControllers();

builder.Services.AddHttpClient<CustomersController>(client =>
{
    client.Timeout = TimeSpan.FromSeconds(30);
});

var app = builder.Build();

app.MapControllers();

app.Run();
```

For larger integrations, a typed client provides better separation between controller logic and third-party communication:

```csharp
public sealed class ThirdPartyCustomerClient
{
    private readonly HttpClient _httpClient;

    public ThirdPartyCustomerClient(HttpClient httpClient)
    {
        _httpClient = httpClient;
    }

    public async Task<HttpResponseMessage> GetCustomerAsync(
        string customerId,
        CancellationToken cancellationToken)
    {
        var requestUri =
            $"legacy/customer?id={Uri.EscapeDataString(customerId)}";

        return await _httpClient.GetAsync(
            requestUri,
            cancellationToken);
    }
}
```

The typed client can be registered with its base address and timeout:

```csharp
builder.Services.AddHttpClient<ThirdPartyCustomerClient>(
    (serviceProvider, client) =>
    {
        var configuration =
            serviceProvider.GetRequiredService<IConfiguration>();

        var baseUrl =
            configuration["ThirdPartyApi:BaseUrl"]
            ?? throw new InvalidOperationException(
                "The third-party API base URL is not configured.");

        client.BaseAddress = new Uri(baseUrl);
        client.Timeout = TimeSpan.FromSeconds(30);
    });
```

## Protecting Third-Party Credentials

One of Achukkowa's most important responsibilities is preventing third-party credentials from leaking into consuming applications.

Credentials should not be:

- Included in source control
- Stored in container images
- Written to application logs
- Returned in error responses
- Supplied by API consumers
- Embedded in gateway route definitions as plain text

The proxy should retrieve credentials from an approved secret-management mechanism at runtime. Access to those secrets should be granted only to the OCI resources that require them.

Credential rotation should not require every consuming application to be updated. Because clients call Achukkowa rather than the third party directly, credentials can be changed inside the proxy environment without altering the internal API contract.

## Request and Response Transformation

Third-party APIs often use contracts that are inconvenient, inconsistent, or unsafe to expose directly.

A proxy can provide a stable internal contract by transforming both requests and responses.

For example, an internal request might use:

```json
{
  "firstName": "Grace",
  "lastName": "Hopper"
}
```

The third party might expect:

```json
{
  "F_NAME": "Grace",
  "L_NAME": "Hopper",
  "SOURCE_SYSTEM": "ACHUKKOWA"
}
```

A C# request model can represent the internal contract:

```csharp
public sealed record CreateCustomerRequest(
    string FirstName,
    string LastName);
```

The proxy can then create the provider-specific payload internally:

```csharp
var providerRequest = new
{
    F_NAME = request.FirstName,
    L_NAME = request.LastName,
    SOURCE_SYSTEM = "ACHUKKOWA"
};
```

This keeps provider-specific fields out of internal applications and makes future migrations easier.

## Handling Errors Consistently

Third-party APIs may return unreliable or inconsistent status codes. For example, a provider might return:

- `200 OK` with an error inside the response body
- `500 Internal Server Error` for invalid input
- `404 Not Found` when authentication fails
- An HTML error page instead of JSON
- No response when the service times out

Achukkowa should translate these failures into a predictable internal error model.

A standardized response might look like this:

```json
{
  "error": {
    "code": "UPSTREAM_SERVICE_UNAVAILABLE",
    "message": "The requested service is temporarily unavailable.",
    "correlationId": "a1841453a39c4e068a5418026e821f42"
  }
}
```

The response should provide enough information for the caller to understand the outcome without exposing credentials, internal URLs, stack traces, or sensitive provider details.

A useful status-code strategy might include:

| Situation | Achukkowa response |
|---|---:|
| Invalid consumer input | `400 Bad Request` |
| Missing or invalid consumer authentication | `401 Unauthorized` |
| Authenticated caller lacks access | `403 Forbidden` |
| Requested internal resource does not exist | `404 Not Found` |
| Third-party service rejects or fails the request | `502 Bad Gateway` |
| Third-party service times out | `504 Gateway Timeout` |
| Unexpected proxy failure | `500 Internal Server Error` |

The exact mapping should be documented for each integration.

## Logging and Correlation

Because Achukkowa sits between consumers and third-party services, request correlation is essential.

Each incoming request should have a correlation identifier. If the caller supplies an approved correlation header, the proxy may preserve it. Otherwise, the gateway or proxy can generate one.

The identifier should appear in:

- OCI API Gateway logs
- Proxy application logs
- Error responses
- Outbound third-party request logs, where appropriate

A simple middleware component can add correlation support:

```csharp
public sealed class CorrelationIdMiddleware
{
    private const string HeaderName = "X-Correlation-ID";

    private readonly RequestDelegate _next;

    public CorrelationIdMiddleware(RequestDelegate next)
    {
        _next = next;
    }

    public async Task InvokeAsync(
        HttpContext context,
        ILogger<CorrelationIdMiddleware> logger)
    {
        var correlationId =
            context.Request.Headers.TryGetValue(
                HeaderName,
                out var existingValue)
                ? existingValue.ToString()
                : Guid.NewGuid().ToString("N");

        context.Response.Headers[HeaderName] = correlationId;

        using (logger.BeginScope(
            new Dictionary<string, object>
            {
                ["CorrelationId"] = correlationId
            }))
        {
            await _next(context);
        }
    }
}
```

Register it early in the request pipeline:

```csharp
app.UseMiddleware<CorrelationIdMiddleware>();
app.MapControllers();
```

Logs should never contain authorization headers, API keys, session tokens, passwords, or complete payloads containing sensitive data.

## Timeouts, Retries, and Resilience

A proxy must assume that an external provider will occasionally be slow or unavailable.

At a minimum, integrations should define:

- A connection timeout
- An overall request timeout
- Retry rules for transient failures
- Maximum retry counts
- Backoff behavior
- Circuit-breaking behavior
- Limits on request and response sizes

Retries should be used carefully. Automatically retrying a `GET` request is usually safer than retrying a request that creates a payment, submits an order, or updates a customer.

A retry on a non-idempotent operation could cause the same transaction to be processed more than once.

The proxy should also avoid waiting indefinitely for a provider. A controlled timeout lets Achukkowa return a consistent `504 Gateway Timeout` response rather than consuming container resources until the connection fails.

## Health Checks

Each containerized proxy should expose health endpoints, such as:

```http
GET /health/live
GET /health/ready
```

A basic health response could be:

```json
{
  "status": "healthy"
}
```

It is useful to distinguish between two types of checks:

- **Liveness checks** confirm that the C# process is running.
- **Readiness checks** confirm that the proxy is ready to accept traffic.

A readiness check should be designed carefully. Calling the third-party API during every health check may create unnecessary traffic or cause the proxy to appear unhealthy whenever the provider experiences a temporary outage.

## Containerizing the Proxy

A basic multi-stage Dockerfile for an ASP.NET Core proxy might look like this:

```dockerfile
FROM mcr.microsoft.com/dotnet/sdk:8.0 AS build
WORKDIR /src

COPY ["Achukkowa.Proxy.csproj", "./"]
RUN dotnet restore "Achukkowa.Proxy.csproj"

COPY . .
RUN dotnet publish "Achukkowa.Proxy.csproj" \
    --configuration Release \
    --output /app/publish \
    --no-restore

FROM mcr.microsoft.com/dotnet/aspnet:8.0 AS runtime
WORKDIR /app

COPY --from=build /app/publish .

EXPOSE 8080

ENV ASPNETCORE_URLS=http://+:8080

ENTRYPOINT ["dotnet", "Achukkowa.Proxy.dll"]
```

The resulting image can be stored in an OCI-compatible container registry and deployed to OCI Container Instances.

Runtime configuration should be supplied through the deployment environment rather than baked into the image.

## API Gateway Routing

OCI API Gateway maps a consumer-facing route to the appropriate container backend.

A conceptual route might look like this:

```text
GET /customer-api/customers/{customerId}
```

The route forwards traffic to the customer proxy running in an OCI Container Instance:

```text
http://<container-backend>/customers/{customerId}
```

The public route and backend route do not need to match exactly. This allows the gateway to expose a clean, versioned interface while the container uses routes that are convenient for the C# application.

For example:

```text
/v1/customers/{customerId}
```

could map to:

```text
/internal/provider-a/customer/{customerId}
```

Consumers should depend only on the public Achukkowa contract.

## Security Boundaries

Achukkowa improves third-party integration security, but it should not be treated as a simple forwarding service.

Each proxy should explicitly control:

- Which routes are available
- Which HTTP methods are accepted
- Which headers may be forwarded
- Which query parameters are allowed
- Which request fields are permitted
- Which response fields are returned
- Which destination hosts may be contacted

Avoid creating a generic endpoint that accepts an arbitrary target URL. That design could allow the proxy to be abused to contact unapproved internal or external systems.

The third-party destination should be fixed through configuration, and caller-supplied paths should be validated against an allowlist.

Headers should also be handled deliberately. A proxy should not automatically forward every incoming header. Instead, it should copy only headers that are required and safe for the third-party integration.

## Deployment Considerations

Before deploying a new Achukkowa proxy, verify the following:

- The container image has been built from an approved base image.
- The image has passed vulnerability and dependency scans.
- The proxy listens on the expected port.
- Required environment variables and secrets are available.
- The container can reach only the required third-party destinations.
- The API Gateway route points to the correct backend.
- Authentication and authorization policies are configured.
- Health endpoints are available.
- Timeouts are aligned across the gateway, proxy, and provider.
- Logs do not expose credentials or sensitive payload data.
- Alerts exist for elevated failure rates and latency.
- A rollback procedure has been documented and tested.

Deployment changes should be versioned and repeatable. Infrastructure and gateway definitions should be managed through an approved automated process wherever possible rather than being configured manually.

## Observability

A secure proxy is only useful if the team can tell whether it is functioning correctly.

Useful metrics include:

- Request count
- Successful request count
- Client-error count
- Upstream-error count
- Request latency
- Upstream latency
- Timeout count
- Retry count
- Circuit-breaker state
- Container CPU and memory usage

Metrics should distinguish between problems caused by Achukkowa and problems caused by the external provider.

For example, a rise in `502 Bad Gateway` responses combined with increased upstream latency may indicate a provider outage. A rise in internal `500` responses may instead indicate a problem in the C# proxy.

## Testing an Integration

Testing should cover more than the successful request path.

Recommended scenarios include:

1. A valid request with a successful provider response
2. Invalid or missing consumer authentication
3. A caller without permission to access the route
4. Invalid request fields
5. A provider authentication failure
6. A provider timeout
7. A provider `500` response
8. A malformed provider response
9. A response containing fields that must be filtered
10. A request exceeding the permitted payload size
11. A repeated request for an idempotent operation
12. A repeated request for a non-idempotent operation

Integration tests should confirm both the API contract and the security boundary. A request should not be able to change the upstream host, inject credentials, forward unauthorized headers, or access an undocumented provider operation.

## Versioning the API

Consumers should not need to change whenever a third-party provider changes its API.

Achukkowa can isolate those changes behind a versioned internal contract:

```text
/v1/customers/{customerId}
```

A breaking change can be introduced through a new version:

```text
/v2/customers/{customerId}
```

Internally, both versions might communicate with the same provider or with completely different providers.

Versioning gives consumers time to migrate while allowing the proxy implementation to evolve independently.

## What Achukkowa Should Not Become

Achukkowa should not become:

- An unrestricted HTTP forwarding service
- A place to bypass normal security reviews
- A permanent store for third-party data
- A substitute for strong security from the provider
- A location for unrelated business logic
- A single generic proxy with access to every provider
- A mechanism for exposing arbitrary internal or external endpoints

Its purpose is to provide a narrow, controlled, observable, and maintainable security boundary around third-party integrations.

## Recommended Development Workflow

A typical workflow for adding an integration is:

1. Document the third-party API and its security weaknesses.
2. Define the internal API contract consumers should use.
3. Identify the required routes and HTTP methods.
4. Define request and response transformations.
5. Determine how provider credentials will be stored and retrieved.
6. Implement the C# proxy using typed models and clients.
7. Add validation, timeouts, error mapping, and correlation.
8. Build and scan the container image.
9. Deploy the image to OCI Container Instances.
10. Configure the OCI API Gateway routes and policies.
11. Test successful and unsuccessful request paths.
12. Add dashboards, logs, and alerts.
13. Publish consumer documentation.
14. Complete the required review and approval process.

## Final Thoughts

The Achukkowa API Gateway allows internal applications to use third-party APIs without inheriting all of their security and design limitations.

OCI API Gateway provides a managed entry point for routing and access control. OCI Container Instances provide a lightweight runtime for C# proxy services. Together, they create a boundary where credentials can be protected, requests can be validated, responses can be normalized, and external dependencies can be observed.

The most important principle is that Achukkowa should do more than forward traffic. Every integration should expose a deliberate internal contract, restrict access to approved operations, protect provider credentials, and fail in a predictable way.

When implemented with those principles, Achukkowa turns an insecure or inconsistent third-party API into a controlled service that internal applications can consume safely.
